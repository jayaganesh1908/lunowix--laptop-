2026-09-27 — Playwright in CI, and three test-design bugs
----------------------------------------------------------
The 12 browser checks from the backend pass had been run by hand and left out of
CI. They are in now: 17 tests in e2e/, a separate job with a matrix over both
storage adapters, Playwright's own webServer serving the PRODUCTION build rather
than next dev — two of the bugs these guard against only appear in a production
build.

WHAT THEY COVER
  product-cards  The two bugs that shipped invisibly: a toast swallowed by a
                 duplicate context, and a heart button covered by the card's
                 stretched link. A passing toast proves both, since the click has
                 to reach the button and the button has to reach a mounted
                 provider. Plus: the click must not navigate, and a save must
                 survive a reload.
  account        Register, localStorage merge into the account, the role-matched
                 admin page, a second account refused with 403, writing a review,
                 sign out keeping the browser's saved products, the review staying
                 public while the form is gated, a wrong password refused, and
                 signing back in.
  health         /api/health reporting the live adapter, the products API
                 validating its query string by CONTENTS not just status, 401 on
                 protected routes, and a forged cookie rejected.

THREE BUGS, all mine, all in the tests rather than the app
  1. Playwright gives every test a fresh browser context, so a `serial` describe
     shares execution ORDER but not session STATE. The account registered in the
     first test was signed out by the second, and the navbar assertion failed
     looking for a menu that correctly was not there. One shared context in
     beforeAll fixes it.
  2. The admin test asserted the admin path unconditionally, which only holds on
     a virgin database — the first account becomes the admin, so the second local
     run produced a member and failed for a reason unrelated to the app. It now
     reads the assigned role and asserts the matching UI, and a second account
     covers the member path deterministically.
  3. `getByRole("alert")` is ambiguous in any Next.js app: the framework always
     renders an empty <div role="alert" id="__next-route-announcer__">, so the
     query resolved to two elements and failed strict mode — reporting a selector
     problem as though the message never appeared. Scoped to the form.

ALSO
  .gitignore had `Thumbs.db.data/` on one line — an earlier append landed on a
  file with no trailing newline, so `.data/` was never actually ignored and a
  local run could have committed users.json, scrypt hashes and all. Repaired and
  verified with git check-ignore.

  playwright.config.ts takes E2E_CHROMIUM_PATH, for environments that have a
  Chromium but cannot download one. Playwright pins an exact browser build per
  release, so a pre-installed browser from another version is refused even though
  a working one is on disk.

Verified locally 17/17 three ways: fresh Postgres (admin path), the same Postgres
again (member path), and the file store.


2026-09-27 — CI, and a lint step that was passing on warnings
-------------------------------------------------------------
The repository had no .github/workflows at all, so the 89 tests only ever ran
when somebody typed `npm test`. Added .github/workflows/ci.yml: install, lint,
typecheck, the suite TWICE — file store, then a postgres:16 service container —
then the build, on every pull request and every push to main.

Running it on both adapters is the point rather than thoroughness for its own
sake: they sit behind one Store interface and the whole claim of that seam is
that the repositories above it behave identically on either. A green run on one
adapter does not check that.

Found while verifying each step actually fails on a regression: `npm run lint`
exited 0 with an unused variable present. ESLint exits 0 when there are only
warnings, and this config reports unused vars and imports as warnings — so the
lint step would have printed them and passed. Worse than no lint step, because
it looks like coverage. The script now carries --max-warnings 0, set in
package.json rather than in the workflow so a contributor gets the same verdict
locally.

Verified by probe: a failing test exits 1, a type error exits 2, an unused
variable now exits 1, and a clean tree exits 0 on all three. Every CI step was
also run verbatim against a local Postgres on 5432 with password auth, matching
the service container: 100/100 and a clean build.

No AUTH_SECRET in the build step, deliberately. It is a runtime requirement of
`next start` and the build does not read it; a placeholder would hide a
regression where something started reading it during the build.


2026-09-27 — Backend, and four bugs found while verifying it
-------------------------------------------------------------
The site had no backend since Supabase was removed: sign-in was front-end only,
/auth/register said "accounts aren't live", the wishlist lived in localStorage,
the newsletter ran an 800ms timer and claimed success, and the admin dashboard
reported 4,820 users from a static array on a site with none.

BACKEND
  lib/server/store    One `Store` interface, two adapters. DATABASE_URL set ->
                      Postgres (one jsonb `documents` table, GIN-indexed);
                      unset -> JSON files under .data/, so a fresh clone runs
                      with no setup. Every repository above the seam is written
                      ONCE and runs unchanged on either. Refuses to hand back the
                      file store on a detected serverless host, where writes do
                      not survive between requests.

  lib/server/auth     scrypt at N=2^16 from node:crypto, cost parameters stored
                      with the hash so they can be raised later. Sessions are a
                      random 32-byte id stored server-side, handed out in an
                      HMAC-signed httpOnly cookie — the signature rejects a
                      forged cookie without a database round trip.

  lib/server/repo     users, sessions, wishlist, compareHistory, reviews,
                      newsletter, views, passwordResets.

  app/api             16 routes. Auth (register/login/logout/session, plus a real
                      password reset with single-use hashed tokens), wishlist
                      with a merge endpoint, compare history, per-product
                      reviews, newsletter, products, admin stats and users, and
                      /api/health.

  Sign-in answers identically for an unknown address and a wrong password, and
  spends the same time on both. Rate limiting on every auth and mail endpoint.
  AUTH_SECRET is REQUIRED in production and the app refuses to sign sessions
  without it — a per-process fallback would sign cookies the next deploy could
  not verify.

  The catalogue deliberately stays in lib/data. It is identical for every
  visitor, and keeping it out of the database is what preserves all 74 static
  detail pages.

FRONT END
  Real sign-in and registration; wishlist and compare still work signed out and
  merge into the account on sign-in (a union, never a replacement); reviews you
  can write, edit and delete; a working newsletter; an account menu with sign
  out; and live admin figures replacing the invented ones.

FOUR BUGS, all pre-existing, all found by verifying rather than by reading
  1. Duplicate ToastContext. components/providers/index.tsx called
     createContext() a second time, so `useToast` imported from the barrel hit
     its no-op fallback. Every wishlist and compare toast on /phones,
     /headphones, /products, /search and the home row was silently swallowed;
     laptop cards, importing directly, worked.

  2. Card buttons were unclickable. The title's stretched link
     (after:absolute after:inset-0) had no z-index and came later in the DOM
     than the wishlist/compare strip, so it painted over both controls across
     the whole card. Clicking the heart navigated instead of saving, on every
     grid, on both card components. Found by Playwright reporting which element
     actually receives the click.

  3. formatCompact was not deterministic. Intl compact notation for en-IN gives
     "8.6K" on Node's ICU and "8.6T" on Chromium's newer CLDR, where T means
     thousand. Server and client rendered different text, /admin failed
     hydration and regenerated the subtree, and "8.6T" reads as trillions.
     Replaced with arithmetic (K/L/Cr), matching formatPriceShort.

  4. lib/utils/index.ts was a second full copy of four sibling modules — all 16
     formatters, every animation variant, cn and filterParams. Both copies were
     live depending on how a file wrote its import, which is why bug 3 would
     have needed fixing twice. Collapsed to a re-export barrel.

  Also: 1 critical + 4 high npm advisories cleared (Next 15.5.22 -> 15.5.26);
  the byte-identical demoUsers block removed from lib/data/index.ts; two dead
  files deleted (HomeSections.tsx, LaptopDetailSections.tsx, zero references).

TESTS
  23 -> 89 (100 with a test database). New: scrypt hashing including malformed
  input and parameter upgrades, session signing and tamper rejection, the file
  store including a concurrency test for the write lock, every repository,
  client/server validation parity, formatCompact determinism, and 11 Postgres
  adapter tests against a real server (jsonb null containment, bigint counts,
  upsert on conflict, injection-resistant values).

  Verified end to end in Chromium on BOTH adapters: 12/12, zero console errors.

BUNDLE
  Sharing zod schemas with the forms added ~74 KB to first load on every product
  page. The rules moved to lib/validation/rules.ts as plain constants and pure
  functions; the server builds its zod schemas from the same constants and
  parity is now a tested property. Product pages 305 kB -> 236 kB.


2026-08-14 — Light mode surface pass (design-audit, Phases 1-3)
---------------------------------------------------------------
Light mode had never received the treatment dark mode got, and lagged badly.

PHASE 1 (critical) — one token, three findings resolved
  --color-ink-50: #FEFFD2 -> #F5F1DE

    page -> card gap          1.08 -> 5.01 L*      (target >= 4)
    page chroma               22.7 -> 9.8
    header glass vs page      0.80 -> 3.70 L*
    image well recess on card 1.10 -> 5.00 L*

  Light mode has no headroom on the card side (white is the ceiling), so the
  ground had to come down. ink-50 is also the image well and footer ground, so
  all three moved together with no component edits.

  Unchanged, verified: body text 17.55:1, muted 7.57:1, brand eyebrow 4.79:1,
  badge chip 6 L* recess, and all of dark mode (page 15.5, card 5.4, gap 10.09).

PHASE 2 (refinement)
  Footer band was a provable no-op: bg-ink-50/60 over an ink-50 page composites
  to the page exactly (-0.15 L*). Changed to a neutral scrim bg-ink-900/5,
  matching how the dark variant already works.
    footer band vs page       -0.15 -> 3.87 L*   (dark: 4.07 L*)

PHASE 3 (polish)
  --card-glow-strength (light): 0.16 -> 0.24
  In light the bloom darkens its ground, so a deeper page gave the same orange
  less room. Peak had fallen 5.70 -> 5.12 L*; 0.24 restores it at 7.63 L*.
  Deliberately still under dark's 17.0 — see DESIGN_SYSTEM.md.

  Badge chip left alone (already correct at 6 L* recess).

  Broke every route mid-phase with a JSX comment before a root element
  (HTTP 500). Fixed; recorded in LESSONS.md.
